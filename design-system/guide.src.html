DCS Workbench Design System

The design system for our internal developer tools — DCSPad, SP Workbench, Halo, and whatever comes next.
v1.0dark onlyno build stepno CDN

It is deliberately not BMO and not SharePoint: when a page looks like this, you are inside a specialised instrument built by and for this team. End-user app UI stays in the BMO design system. This is the other thing.

It is the DCSPad token set, codified — nothing in DCSPad is deprecated. Everything new is additive, and every recommended change to an existing repo is listed, with a reason, under Recommended upgrades.

Start

How to use it

Three ways in, in order of how much of the system you want. Pick one — they do not mix well in the same file.

1 · Link the sheet

One stylesheet, every token and every .dcs-* class. For a repo-backed tool that can reference files.

<link rel="stylesheet" href="styles.css">
2 · Paste it inline

Copy assets/dcs-workbench.standalone.css into a <style> block. The tool stays a single file you can email, and still looks like family.

3 · Start from a template

templates/dcspad, templates/sp-workbench (L1) or templates/compact-tool (L2) — real shells with the chrome already right. See Templates.

The one contract

Tools get copied, inlined and edited in place. That is fine. Keep the token names even when you paste the values. A drifted teal is still family; a renamed --brand-green can never be swept back in.

Start

Six rules that make everything else fall out

  • Sharper than its host. It lives inside corporate SharePoint. It should read as a precision instrument dropped onto that page — never as a themed SharePoint page, and never as a decorated one.
  • One accent, used once. Teal is structural: rails, hairlines, active states, glyphs. A solid accent fill appears exactly once per screen, on the verb that runs the thing.
  • Colour is information. Signals mean status. File type is a colour. Folder role is a colour. If a colour tells you nothing, the element is grey.
  • Hierarchy by surface, not shadow. Four greys stack: ground, panel, chrome, hover. Hairlines separate. One shadow exists and it means "floating above the app."
  • Mono means machine. Anything a machine produced or will consume — paths, GUIDs, sizes, statuses, code — is monospace. Everything a human wrote is sans.
  • Copy-safe by design. No build step, no CDN, no icon package. A tool can be a single HTML file with the tokens pasted inline and still be unmistakably part of the family.

Foundations

Colour

One accent hue and nothing else decorative. Solid --accent fill appears exactly once per screen — on the verb that runs the tool. Everywhere else the accent is a hairline, a rail, a glyph, or a soft wash.

Dark only. There is no light theme and there should not be one — the contrast with the host page is the point.

The rules behind the swatches

  • Surfaces step in order and are never skipped. Need more contrast? Add a hairline, don't jump a step. --bg-editor is the code ground and matches the Monaco theme exactly.
  • --fg-faint is timestamps and hints. It is never body copy — at ≈3.5:1 on --bg-1 that rule is doing real work.
  • Signals mean status and never decorate. Red text on the plain panel ground is the anti-pattern; every signal has a wash to sit on.
  • File type has five buckets — JS, HTML, CSS, Data, Document. Anything else stays grey; a sixth hue needs a sixth pane to justify it. Near relatives inherit: .ts→JS, .scss→CSS, .svg→HTML, .csv/.xlsx→Data.
  • Node glyphs have two tiers. The bare token is the resting state, because rest is what the whole list does. You opt into brightness with -active via .is-called-out, and only for a row that is doing something.
Foundations

Type

Two families; nothing is downloaded, which is what lets a tool be a single copyable file. --sans: "Segoe UI" for prose and UI labels — every machine that runs these tools has it, so it is referenced, never shipped. --mono: "Cascadia Code", "Consolas", "SF Mono", Menlo, monospace for anything a machine produced or will consume.

Panel and group titles are uppercase, 10px (9.5px in L2), 700, .14em, --fg-dim. Always — and never for anything longer than three words.

Ligatures are on

Cascadia Code's coding ligatures — => !== <= -> :: — are contextual alternates, on by default but silently dropped by input, textarea and select, and switchable off by a host page. The system states it: --mono-ligatures / --mono-features, applied by base.css and, for a web part that cannot ship it, by dcs-additions.css § 6 on .dcs-app / .dcs-tool and their descendants. Those selectors carry real specificity on purpose — the font: shorthand resets font-variant-*, so a :where() rule loses to every font: var(--t-*) in the sheet. Use .dcs-liga to opt in outside a shell, .dcs-liga-off where a ligature is wrong — a character-by-character diff.

Foundations

Space, shape, elevation

A 2px base, but only these values ship: 2 · 4 · 6 · 8 · 10 · 12 · 14 · 16 · 20 · 24. Gutters between panes are always 5px — that is the splitter track, a control, not a spacing step.

Cards, borders, hover, press, focus

A "card" here is a panel: flat --bg-1, a 1px opaque --border hairline, radius 4 (6 for a shell, menu or dialog), no shadow, no gradient, no coloured left border. Hairlines are opaque — never rgba — so they read identically over every surface step. Interactive edges step up to --border-strong.

Hover changes colour, never size. No transform, no shadow, no border-width change — nothing that shifts layout. Row tools fade in with opacity, not visibility, so they stay clickable and testable. Selected rows keep a resting state (accent rail + chrome ground) so selection survives losing hover. Press is the same wash one step darker; there is no scale-down. Focus is :focus-visible only — --accent-soft-line outline plus a 2px --accent-ring wash. Mouse clicks never light a ring.

Backgrounds and imagery

No images, no gradients, no textures, no blur. Depth comes from four flat greys, hairlines, and the one shadow. The only patterned surface in the system is the L2 canvas stage: a 24px hairline lattice, so an artboard's real edges read against the dark ground. Transparency appears in exactly four places — the shadow, the dialog backdrop, the skeleton shimmer, and disabled opacity. There is no photography and no illustration anywhere in this system, including in empty states, deliberately.

Foundations

Motion

Four beats, nothing outside them, because motion in a developer tool is feedback rather than personality. Easing is cubic-bezier(.35, 0, .25, 1).

Foundations

Icons & brand

There is no icon package. Tools get copied around and inlined; a CDN icon font would drift or break. So icons are inline SVG and consistency comes from one hard rule instead of one library.

  • Copy from DCSPad first, Lucide second, draw third. Paste Lucide SVG as-is — keep its viewBox="0 0 24 24" and stroke-width="2", set width/height to 15–16, delete the class attributes. Do not install the package; do not fetch from a CDN.
  • No emoji. Ever. Emoji folder icons are exactly what the node glyph system replaced. No filled glyph among the line ones either — the exceptions are the solid play triangle on the Run verb, PinGlyph, and the six-dot DragGlyph.
  • One gear, and it is Lucide's. <Icon name="settings" /> is the single gear; advanced is an alias of it. Two shapes for one idea is the drift this rule prevents.
  • Microsoft product marks are not system glyphs. <ProductGlyph name="copilot" | "sharepoint" /> holds the two that remain — trademarks, used only where the control opens the product they name, never recoloured into the accent. The SharePoint mark in Icon is the one exception: it is drawn to the system's own rule.
  • Three ways to ship the same shapes: <Icon name="…"> from the bundle, assets/icons.svg as a <symbol> sprite, or assets/icons.js — the same sprite, self-injecting, for pages that cannot reference an external <use> target.

Brand marks

No logo file exists and none was drawn. Identity is a letter on a 4 × 5 pixel grid inside a tinted tile, the 2×2 instrument mark for L2, and the split-weight mono wordmark. Anywhere a logo would go, set the tool's name in the mono wordmark.

Build

Embedding — living inside SharePoint without pretending to be it

L1 · Takeover

The suite bar stays visible. That is deliberate: it says "this is running on your SharePoint, under your account." It is desaturated while the tool runs so it never competes. The app pins itself at inset: 53px 5px 5px and paints the surround itself with box-shadow: 0 0 0 100vmax — SP wrappers behind the gap have white backgrounds you cannot chase class-by-class. No outline on the app: the 5px gap and the 6px radius do that work.

Always ship a suspend path

When the host page enters edit mode, hide the tool and revert the global html/body overrides — or the editor canvas goes dark and unscrollable.

L2 · In a web part

Scope every rule. Never set html, body, or bare element selectors — the host page owns those, and a stray body { overflow: hidden } makes the whole page unscrollable. Declare tokens on the tool root, not :root: .dcs-tool { --accent: … }. That also lets two tools coexist on one page. Set an explicit min-height so the canvas doesn't collapse before content arrives, and stack the controls above the canvas below 720px.

base.css is for L1 takeover pages, the specimen cards, and the templates. An L2 web part imports tokens/*.css + dcs-workbench.css (+ dcs-additions.css) only.

Practice

Copy voice

A good engineer explaining a thing once, precisely, and then stopping.

  • Sentence case everywhere except panel/group titles and chip labels, which are uppercase with tracking. Never title case.
  • Second person, implied. "Enter an absolute https:// URL on this tenant." Not "Please enter…", not "The user must enter…". No "we".
  • Say the system state, not a feeling. "403 — the request digest expired. Retrying once." Not "Oops! Something went wrong."
  • Lead with the machine fact. Error strings start with the code: 404 — that list does not exist on this web.
  • Empty states are one centred monospace line saying what would appear here and how to make it appear. No illustration, no mascot, no call-to-action card.
  • Notices name the specific object. "This folder already contains a file with that name." "Uploaded to /Code/tools/dcspad · v2.0."
  • Truncation and caps are disclosed, never silent: "Results are capped at 100 — a nextLink is available."
  • Buttons are verbs, one or two words: Run, Generate, Inspect, Export JS, Save snippet. The primary button names the thing it produces.
  • Units and paths inline, in mono, in the sentence: 243.9 KB · 2026-07-31.
  • No exclamation marks, no emoji, no jokes in UI copy. Wit belongs in documentation, not in a status bar.
  • Keyboard convention stated once and honoured everywhere: Ctrl/Cmd + Enter always runs; Esc always steps back one level. Never bind a plain letter key.

Caveats

  • No logo file was provided and none was drawn. The letter marks are the 4 × 5 grid strings the source document specifies, rendered — they are the spec, not an interpretation.
  • One webfont, added on request. The system references installed fonts by design. tokens/fonts.css is the exception: the real Cascadia Code (variable, 200–700), SIL OFL 1.1. The src leads with local("Cascadia Code"), so an installed copy still wins and a pasted-elsewhere tool falls back to Consolas / SF Mono / Menlo exactly as before. Segoe UI is simply referenced — it is on every machine that runs these tools, so there is nothing to ship.
  • dcs-workbench.css is the source sheet verbatim, minus its :root block, which moved to tokens/*.css so the compiler can index it. No value, name or rule was altered. assets/dcs-workbench.standalone.css is the untouched original.
  • The L2 comp inlines its own round-thumb slider (.hslider) which differs from .dcs-slider in the sheet. The kit uses the sheet's version, since that is the named component; flagged rather than reconciled.
  • Contrast, flagged not changed: --fg-faint on --bg-1 measures ≈3.5:1 — under WCAG AA for body text, fine for the incidental use the system assigns it.
  • Open decisions from the 2026-08-02 audit — bare element selectors in the sheet vs the L2 scoping rule; the .dcs-canvas-stage comment saying 8px where it draws 24px; two ADDED accent tokens the verbatim sheet cannot adopt; no sprite symbols for the two filled glyphs; dialogs seating a 26px Cancel beside a 28px primary; .dcs-chip being cursor: pointer even when inert. None breaks anything today. Full text in readme.md.
